# open-vibrotato / vibrotato 2.3.1 优化建议

审阅日期：2026-09-11。以下为源码审阅建议，尚未实施，也未测量性能收益。

## 首次上传前验证（更名前）

- 在临时副本中执行 `python3 tests/verify.py --simulation-only`，退出码为 0。
- 生产逻辑 53 / 53 组、1,965 条断言通过；独立近战与光效 24 / 24 组、4,021 条断言通过。
- JavaScript 语法检查通过，重新构建的 `vibrotato.html` 与现有文件逐字节一致。
- 首次上传时原发布包清单覆盖的 55 个文件全部匹配；更名后更新了清单，旧基线归档在 `docs/previous-2.3.1/`。
- 本次未重跑浏览器与实体设备测试；现有浏览器报告和截图为随项目提供的历史证据。

## 1. 优先让测试能在不同机器和 CI 上复现

位置：`tests/starform_browser.py:38`、`tests/verify_base.py:72`、`build.py`。

新增浏览器测试写死了 `/usr/bin/chromium`，基础测试已有 `CHROMIUM_PATH` 覆盖入口，两者不一致。建议统一浏览器启动配置，默认使用 Playwright 管理的浏览器，同时保留显式路径覆盖；补充开发依赖及安装说明，再接入 GitHub Actions。

先让每次提交自动执行语法检查、构建和现有 77 组逻辑检查；浏览器检查放入独立任务，并保留失败日志与截图。构建后检查工作树中的 HTML 是否变化，可以发现“源码已改、离线包未更新”。Playwright 的浏览器版本与其包版本相关，应随依赖更新同步安装。[Playwright 官方浏览器说明](https://playwright.dev/python/docs/browsers)

验收：全新环境按文档即可复现；浏览器不可用时明确失败或标注受阻，不能用历史报告代替本次执行。

## 2. 缓存稳定属性，减少每步完整重算

位置：`src/game.js:120` 的 `statSheet()`、`:136` 的 `recalculate()`、`:624` 的调用。

当前每个模拟步都会重新统计武器标签、遍历道具和核心，并创建属性对象与来源列表。建议缓存装备、角色、升级决定的基础属性，只在配装变化时重算；将战斗中的动态加成单独更新。

需要覆盖金库余额档位、猩红生命阈值、寄生奖励到期等触发条件，不能只在购买装备时刷新。属性面板的来源说明可以按需生成。

验收：固定种子下伤害、生命、经济、出手次数及核心触发结果保持一致；在相同场景中比较模拟耗时与分配量，再决定是否保留改动。

## 3. 减少战斗循环的临时数组和重复查询

位置：`src/game.js:87` 的 `SpatialHash`、`:243` 的 `bladeHome()`、`:542` 的 `updateBullets()`、`:791` 的 `updateEffects()`。

`SpatialHash.near()` 每次查询都分配结果数组；近战挂点重复筛选武器；子弹和特效清理频繁通过 `filter()` 创建新数组。这些是候选热点，需要先用浏览器性能分析确认占比。

可优先缓存配装对应的近战槽位表；为空间查询提供调用方独占的可复用结果缓冲；对高频集合使用保持顺序的原地压缩。确认对象分配造成明显停顿后，再考虑子弹与粒子对象池。

验收：攻击顺序、命中去重、空间查询和随机数消费不变；避免嵌套查询覆盖共享缓冲。记录帧耗时的中位数、P95 和垃圾回收停顿，不只看平均 FPS。

## 4. 给低性能设备更明确的画质预算

位置：`src/engine.js:30` 的 WebGL 上下文配置、`:58` 的 `render()`，以及 `src/game.js:99` 的初始画质设置。

项目已使用实例化绘制、预分配实例数组和移动端渲染频率限制，这些机制值得保留。后续可增加低 / 中 / 高画质档位，将内部渲染分辨率、泛光和特效数量分别配置。当前每次渲染都会执行两次泛光模糊；若新增关闭泛光选项，应真正跳过相关处理，并保证合成阶段不会读取旧结果。

`preserveDrawingBuffer` 当前为 `true`，可评估正常游戏是否需要持续保留默认绘图缓冲；修改前验证截图和自动化读图时机。降低内部渲染分辨率是控制像素处理成本的常见方法，具体收益取决于实际设备。[MDN WebGL 性能建议](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#consider_rendering_to_a_smaller_back_buffer)

验收：在真实 Android 和 iOS 设备上比较同一密集战斗场景的帧耗时、画面清晰度与连续运行表现；软件 WebGL 测试只用于功能验证。

## 5. 明确低帧率时的模拟时间策略

位置：`src/game.js:1047` 的 `loop()`。

当前将每帧时间差截断为 50 ms，再划分为不超过约 16.7 ms 的子步。若持续以 10 FPS 运行且不处于顿帧效果中，每秒通常只推进约 0.5 秒模拟时间。这避免了长帧后大量追赶，也会让低帧率下的波次时钟变慢。

建议先确定预期体验，再考虑固定步长累积器、最大追赶步数，以及超过预算时的明确处理策略。保留当前失焦暂停和输入清理。`requestAnimationFrame()` 的回调频率会随屏幕刷新率变化，后台时也可能暂停，不能假定它恒为 60 Hz。[MDN requestAnimationFrame 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)

验收：模拟 10 / 30 / 60 / 120 Hz 与单次长卡顿，比较移动、冷却、波次计时和近战调度；将有意保留的减速行为写入规则。

## 6. 拆分源码职责，保留单文件交付

位置：`src/game.js`，约 100 KB、1,066 行。

当前包含音频、空间索引、经济、战斗、输入与绘制等职责。建议按职责逐步拆分开发源码，由构建脚本继续生成离线单 HTML；先做保持行为不变的拆分，再优化热点。

更名时已将旧版逐字节基线归档，当前版本使用 `tests/source-hashes.json` 校验源码完整性。未来修改这些文件时，应同步更新版本清单并补充相应功能验证，避免直接删除失败断言。新增测试报告与截图也应有明确输出位置，防止开发测试覆盖发布证据。

验收：77 组逻辑检查继续通过；完整浏览器验证通过；源码修改能够稳定、可复现地生成离线产物。
